# Incident response и восстановление — Kleo

План, не запущенная служба мониторинга. Ответственный за координацию — владелец Кирилл; контакты провайдеров и дежурства определяются перед публичным пилотом. Не публиковать details, secrets или personal data в открытых обсуждениях.

## Detect → Contain → Revoke → Rotate → Investigate → Restore → Notify → Review

1. **Detect.** Зафиксировать время, сигнал, затронутые версии/проекты и предполагаемый impact. Сохранить минимальные доказательства в приватном месте, с redaction. Не копировать ключ в отчёт.
2. **Contain.** Остановить затронутый workflow/интеграцию, отключить опасное действие или изолировать сервис. Ограничить исходящие вызовы и расход. Сохранять доказательства; не удалять все журналы вслепую.
3. **Revoke.** Отозвать затронутые API/CMS keys, сессии, approvals и привилегии. При компрометации администратора отзывать его активные сессии и проверить действия с credentials/backups.
4. **Rotate.** Выпустить новые минимально привилегированные secrets, поместить их в надлежащее хранилище. Не повторно использовать старые значения. Проверить полномочия и убрать скомпрометированный источник.
5. **Investigate.** Установить вектор, период, версии, проекты и объём доступа/расхода. Проверить журнал провайдера, usage, repository/history, dependencies, интеграции и резервные копии. Отделять установленные факты от гипотез.
6. **Restore.** Исправить причину, проверить регрессионным тестом, восстановить чистую версию/данные в изолированной среде. Проверить tenant mapping и интеграции с новыми ключами; открывать доступ постепенно.
7. **Notify.** Владелец определяет пострадавших, приватные каналы, договорные и применимые правовые обязательства вместе с профильным специалистом. Не выдумывать универсальные сроки уведомления. Сообщать проверенные факты и действия без секретов.
8. **Review.** Приватный postmortem: timeline, cause, impact, detection gaps, исправления с ответственными и сроками. Добавить тест и обновить threat model/checklist. Проверить завершение корректирующих действий.

## Если утёк API key

Сначала revoke у провайдера; затем rotate. Найти следы в текущих файлах, Git history, архивах, CI/debug/logs и share links без печати самого ключа. Проверить usage и неожиданные запросы/списания. Отключить или повторно авторизовать затронутые интеграции, сменить связанные credentials при общей компрометации. Оформить postmortem. Удаление ключа из файла не делает его снова безопасным. Изменение общей Git history планируется отдельно после отзыва, с координацией копий и форков.

## Backup / recovery rules — Planned

- Резервные копии хранятся отдельно от primary server и его учётной записи. Production backups сейчас не настроены.
- Шифрование при передаче и хранении; ключ восстановления отдельно, доступ по least privilege. У обычного приложения нет права удалить все backup versions.
- Версионирование и неизменяемое/защищённое хранение по согласованному сроку. Не включать `.env` и raw credentials в обычный архив проекта; восстановление секретов через отдельную процедуру.
- До пилота определить RPO (допустимая потеря данных) и RTO (время восстановления) и подтвердить испытанием, не обещать их без замеров.
- Restore procedure: выбрать проверенную версию → изолированная среда → проверить целостность и расшифрование → восстановить данные/версии/memberships → подключить новые credentials → тест прав и содержимого → согласовать переключение → наблюдать → сохранить итоговый отчёт.
- Регулярно проверять восстановление, включая потерю primary server и компрометацию admin. Обычная успешная запись backup не доказывает возможность restore.
